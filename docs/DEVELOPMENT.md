# Система керування готелями

## Запуск

Потрібні Java 17+ та Maven 3.6.3+ або Docker Desktop із Linux Engine.

```sh
./mvnw verify
./mvnw spring-boot:run
```

У PowerShell використовуйте `.\mvnw.cmd verify` та `.\mvnw.cmd spring-boot:run`; JDK має бути в JAVA_HOME. Maven Wrapper завантажує Maven 3.9.11 автоматично.

Або з кореня проєкту:

```sh
docker compose up --build -d
```

Відкрити http://localhost:8080. Перший екран створює Адміна за email і паролем (щонайменше 10 символів, не більше 72 байтів UTF-8). Початкових паролів і демонстраційних облікових записів немає. Адмін додає готелі, потім користувачів. Керуючому обов'язково призначається один готель.

Docker за замовчуванням публікує порт лише на цьому комп'ютері (127.0.0.1). Для перевірки зі смартфона в локальній мережі після початкового налаштування можна змінити прив'язку порту на 8080:8080. Для доступу поза довіреною локальною мережею потрібні HTTPS і окреме налаштування захисту розгортання.

## Ролі

- ADMIN — Адмін: готелі та користувачі.
- ADMINISTRATOR — Адміністратор: пошук, бронювання, зміна дат і скасування до заселення, календар та дохід мережі/готелю.
- MANAGER — Керуючий: номери, оснащення, ціни, заселення, виселення, клінінг та дохід лише свого готелю.

Доступ перевіряється сервером. Приховування кнопок у браузері не є механізмом авторизації. JWT перевіряється Spring Security і перетворюється на HotelToken. Контролери отримують @AuthenticationPrincipal HotelToken, а перевірки виконуються через token.requireRole(Role.ADMIN), token.requireHotelAccess(...), token.hotelFilter(...) і token.requireRevenueAccess(). Ідентичність, роль і готель завантажуються з БД для кожного запиту; зміна ролі діє і для раніше виданого JWT. JWT діє 8 годин, передається у Bearer-заголовку, зберігається в sessionStorage поточної вкладки. Паролі хешуються BCrypt. JWT не містить пароль або дані гостей. Гості не обліковуються взагалі.

## База та міграції

H2 працює у файловому embedded-режимі, без окремого сервера. Файли бази і випадково згенерований JWT-ключ зберігаються в ./data. У Docker ця папка підключена через bind mount. Перезапуск та перестворення контейнера не видаляють її. Для резервної копії зупиніть застосунок і скопіюйте data. Не запускайте дві копії застосунку з однією файловою базою.

Flyway виконує src/main/resources/db/migration/`V1__initial_schema.sql`. Наступні зміни: `V2__description.sql`, `V3__description.sql` тощо. Уже застосовані міграції не редагувати; Flyway перевіряє їх контрольні суми. Hibernate тільки перевіряє схему (ddl-auto=validate), не створює її. У початковій схемі немає CHECK-обмежень: допустимі коди задають Java enum та конвертори, а діапазони значень, дати й призначення готелю перевіряються в DTO та сервісах. Сутності можуть отримувати будь-яке значення свого enum; переліки кодів у SQL не дублюються. PRIMARY KEY, FOREIGN KEY, UNIQUE та NOT NULL зберігаються.

## Правила обліку

- Бронювання займає діапазон [дата заїзду, дата виїзду). Виїзд і наступний заїзд в один день дозволені.
- Перед збереженням і зміною дат сервер блокує рядок номера та повторно перевіряє перетин активних бронювань. Два паралельні запити не можуть створити перетин.
- Пошук показує окремо точну кількість ліжок і більшу. Наявність поточного клінінгу не заважає бронюванню майбутніх дат.
- Бронювання зберігається окремо від поточного операційного стану FREE/OCCUPIED/CLEANING. RESERVED в календарі обчислюється за датами.
- Керуючий вручну виконує заселення, виселення й завершення клінінгу. Автоматичного переведення станів о 12:00 немає.
- Заселення можливе лише у прибраний номер. На дати чинного бронювання потрібне посилання на це бронювання. Заселення без бронювання допускається за відсутності бронювання на поточну дату.
- Ціна фіксується при заселенні, а не при бронюванні. Подальше редагування ціни номера її не змінює.
- Межа облікової доби — 12:00, Europe/Kyiv. Час до 12:00 належить попередній обліковій даті. Кількість ночей — різниця облікових дат заселення і фактичного виселення, мінімум 1 ніч.
- Валовий дохід = зафіксована ціна × фактичні ночі. Запис створюється тільки на переході OCCUPIED → CLEANING та унікальний для проживання. Скасування бронювання не створює дохід.
- Звіт відбирає дохід за часом фактичного виселення у періоді [початок 12:00, кінець 12:00). Це не розподіл доходу по кожній ночі.
- Календар показує бронювання й фактичне проживання разом. При накладці додає обидва підписи та помаранчеву рамку. Клінінг відображає поточну готовність номера й показується на сьогодні.
- Період одного запиту обмежений 366 днями; місткість номера — 1–20 ліжок.

## Структура

Java: src/main/java/ua/edu/hotels/

- data/entity — окремі JPA-сутності з приватними полями та Lombok Getter/Setter.
- data/enums — Role, RoomState, BookingStatus, Equipment; кожен має code та label.
- data/converter — JPA AttributeConverter для збереження enum як INTEGER.
- data/dto — типізовані записи запитів і відповідей, без Map<String, Object>.
- repository — Spring Data JPA-запити та блокування рядка номера.
- service — бізнес-логіка; окремі сервіси готелів, користувачів, номерів, бронювання, проживань, календаря та доходу.
- service/DateRangePolicy, StayCalculator, CalendarDayFactory — незалежні правила для юніт-тестів.
- controller — REST-контролери за ресурсами та спільна обробка помилок.
- config — налаштування Spring Security, JWT та годинника.
- security — незмінний HotelToken із перевірками ролей, доступу до готелю й доходу та конвертор перевіреного JWT у наш principal.

Фронтенд: окремі HTML-сторінки та ES-модулі без Vue, роутера чи інструменту збірки.

- `static/index.html` — вхід і початкове налаштування; підключає `js/pages/login.js`.
- `static/pages/*.html` — розмітка кожного розділу та власний модуль `js/pages/<назва>.js`. Навігація використовує звичайні посилання; сторінки підтримують прямий URL, оновлення та історію браузера.
- `static/fragments/shared.html` — спільні HTML-шаблони меню, діалогу, карток і рядків таблиць.
- `static/fragments/forms.html` — HTML-шаблони полів форм. JS клонує шаблони та заповнює дані через DOM-властивості й `textContent`, без побудови HTML рядками.

JavaScript: src/main/resources/static/js/

- core/rest.js — єдине місце для fetch, URL, HTTP-методів і Bearer-заголовка.
- core/catalog.js — довідники з GET /api/catalog; підписи ролей, станів та оснащення не дублюються у JavaScript.
- core/session.js, state.js, format.js — сесія, стан інтерфейсу та форматування.
- core/page.js — спільний запуск сторінки, перевірка сесії, завантаження шаблонів та оновлення даних; core/routes.js — адреси й доступні розділи для ролей.
- pages — контролери сторінок: заповнюють розмітку даними та підключають події.
- forms — заповнення HTML-форм і перетворення введених даних у запити API.
- ui — спільні компоненти, діалоги, сповіщення, фільтри та оболонка.

HTML-сторінки й шаблони доступні без Bearer-токена, оскільки браузер завантажує їх звичайною навігацією. Дані та зміни захищені авторизацією API. Перевірки ролей у браузері керують навігацією, а не замінюють серверний контроль доступу. Фільтри дат і готелю зберігаються в URL сторінки.

## Enum-коди та API

Код заданий явно, не обчислюється через ordinal(). Існуючий код не можна перевикористовувати чи змінювати без міграції.

| Enum          | Коди                                                      |
| ------------- | --------------------------------------------------------- |
| Role          | ADMIN=0, ADMINISTRATOR=1, MANAGER=2                       |
| RoomState     | FREE=0, OCCUPIED=1, CLEANING=2                            |
| BookingStatus | RESERVED=0, CHECKED_IN=1, COMPLETED=2, CANCELLED=3        |
| Equipment     | KETTLE=0, AIR_CONDITIONER=1, TELEVISION=2, REFRIGERATOR=3 |

У JSON передаються назви enum. Стани й оснащення зберігаються як числові коди через конвертори. Роль користувача — ManyToOne на UserRole у таблиці app_role; зворотний зв’язок UserRole.users — OneToMany. Ключ ролі — стабільний числовий code з enum. Оснащення — Set<Equipment> у сутності Room і таблиця room_equipment у H2. GET /api/catalog повертає групи roles, roomStates, bookingStatuses, equipment; кожний елемент містить name, code, label. Приклад поля номера: equipment: ["KETTLE", "TELEVISION"].

Єдина початкова міграція Flyway V1 створює всю схему, включно з app_role та зовнішнім ключем користувачів. HotelsApplication.setup() після події ApplicationReadyEvent на кожному старті викликає RoleService.initialize(): він проходить Role.values(), додає відсутні записи та оновлює їхні назви без дублювання. Один користувач має одну роль; одна роль може належати багатьом користувачам.

Схему визначає `V1__initial_schema.sql`. Для зміни вже розгорнутої бази додають нову міграцію з наступним номером; застосовані міграції залишають незмінними.

## Тести

JUnit Jupiter + `@ExtendWith(MockitoExtension.class)`. Залежності підмінюються через `@Mock`; сервіси створюються через `@InjectMocks` або конструктор. Запуск у PowerShell: .\mvnw.cmd verify.

- service/, security/ і data/ — юніт-тести без запуску Spring: розрахунки, ролі, дати, бронювання, проживання, звіти, паролі, календар та конвертори.
- Spring-контекст, реальна БД, HTTP-контролери, виконання SQL і фронтенд у тестах не запускаються. Пріоритет — бізнес-рішення, переходи станів, розрахунки, граничні випадки й права доступу; просте делегування репозиторію окремо не тестується.
- support/Fixtures — спільні тестові дані та контрольований годинник. Допоміжні методи для тестування залишаються в src/test; production-класи не отримують методів лише для тестів. Перевірка порядку викликів блокування через Mockito не перевіряє конкурентну поведінку самої БД.

Lombok використовується для конструкторів залежностей і доступу до полів. JPA-сутності не використовують @Data, щоб не створювати неявні equals/hashCode для змінних ідентифікаторів і колекцій. DTO залишаються Java records.
